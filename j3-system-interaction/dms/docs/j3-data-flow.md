# J3 System Interaction — Data Flow & Architecture

This document outlines how J3 (Dashboard & Interaction Layer) integrates with the rest of the Sri Lanka Disaster Management System.

## Architecture Overview

J3 acts as the central hub for human interaction, providing a public portal for citizens and a secure command dashboard for officials. It is a Next.js (App Router) application.

## 1. Authentication (Integration with J4)

Currently, J3 uses mock authentication (`AuthContext`). In production, this will integrate with the Keycloak instance provided by J4.

- **Client ID:** `j3-frontend`
- **Roles Expected from Token:** `ADMIN`, `OFFICER`, `RESOURCE_MANAGER`, `PUBLIC_USER`
- **Action:** J3 will validate the JWT from Keycloak and extract the `realm_access.roles` to populate the UI permissions.

## 2. Event Streams (Integration with J1 & J2)

J3 relies on Apache Kafka for asynchronous communication between microservices.

### A. Topics J3 Consumes (Listens To)
- `j1.sos.raw-reports`: Consumes SOS reports generated by the mobile app (J1). The event bridge forwards them to `dashboard:new-report` for the incoming reports queue.
- `j1.sensor.telemetry`: Consumes sensor updates from J1. The event bridge forwards them to `sensor:telemetry-update` for live monitoring widgets.
- `j2.engine.risk-alerts`: Consumes enriched prediction alerts from J2. The bridge forwards them to `dashboard:risk-alert` and the frontend normalizes the Kafka envelope to show `predictionCategory`, `predictionProbability`, and `considerationScore`.
- `j2.engine.incidents`: Consumes confirmed incident messages from J2. The bridge forwards them to `dashboard:new-incident`.

### B. Topics J3 Produces (Publishes To)
- `j3.portal.raw-reports`: Published when a public user submits a report via `/report-incident`. Consumed by J2 for clustering analysis and by J3 itself to enter the review queue.
- `j3.dashboard.incident-updates`: Published when an officer verifies a report and converts it into a `ConfirmedIncident`, or when incident status changes.
- `j3.dashboard.resource-updates`: Published when a resource manager updates the assignment or status of a resource.

### C. Frontend Socket Events
- `dashboard:new-report`: Incoming SOS reports in the dashboard stream.
- `dashboard:risk-alert`: Enriched risk alerts from `j2.engine.risk-alerts`.
- `dashboard:new-incident`: Confirmed incidents from `j2.engine.incidents`.
- `dashboard:resource-updated`: Resource changes emitted back into the dashboard after `j3.dashboard.resource-updates` is published.

### D. Current Subscription Contract
The live bridge subscribes to `j1.sos.raw-reports`, `j1.sensor.telemetry`, `j2.engine.risk-alerts`, `j2.engine.incidents`, `j3.dashboard.report-updates`, and `j3.dashboard.resource-updates`.
Resource recommendations are reserved for a later enhancement and are not part of the current bridge contract.

## 3. Real-time Updates (Socket.IO)

To avoid continuous polling, the backend should expose a WebSocket/Socket.IO connection to the J3 client.
When the backend consumes a Kafka event (e.g., a new SOS report), it emits a Socket event (`dashboard:new-report`) to the J3 client, which updates the UI state in real-time.

## 4. API Boundaries

J3's frontend expects a RESTful or GraphQL API gateway (Kong) to handle synchronous operations:
- `GET /api/v1/incidents` — Fetch confirmed incidents.
- `PATCH /api/v1/reports/:id/verify` — Officer approves a report.
- `PATCH /api/v1/resources/:id/status` — Manager updates resource.

*Note: In the current implementation, these APIs are mocked as Next.js API routes (`app/api/...`) returning static JSON.*
